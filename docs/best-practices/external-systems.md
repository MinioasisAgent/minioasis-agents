# External systems

Rules `EX-001` to `EX-013`. The format, and the meaning of the made-up "renew a loan" examples, are explained in [`README.md`](README.md).

Koha is the only external system today. `EX-001` to `EX-003` cover contracts and generated clients. `EX-004` to `EX-009` and `EX-013` describe how Minioasis authenticates to Koha; a capability uses that mechanism and does not rebuild it. `EX-010` to `EX-012` apply to every external call.

A change to how authentication, retries, or deadlines work is Level 2 (`CLAUDE.md`, section 5: security, or an exception to these rules). Tuning a value such as the timeout is not.

<a id="EX-001"></a>

## EX-001 Base every provider operation on the checked-in contract

A call to Koha is built from the checked-in contract, never from memory or from a guess about the protocol. A guessed path or field works until the day it silently does not. If an operation you need is absent from the contract or ambiguous in it, stop and ask the maintainer.

```csharp
// BAD: a handwritten call to a path nobody verified
await httpClient.PostAsync($"checkouts/{loanId.Value}/renew", content: null, cancellationToken);

// GOOD: a generated client method, derived from the operation in the contract
var checkout = await client.RenewCheckoutAsync(loanId.Value, cancellationToken);
```

<a id="EX-002"></a>

## EX-002 Never edit the official contract; derive a focused one

`contracts/official_koha_openapi.json` is an immutable reference. It records what Koha offers, so editing it would make the reference lie.

For the operations a capability needs, derive a focused contract, `contracts/<name>.openapi.json`, that copies those operations faithfully from the reference. Keep every integration change consistent with its source contract.

```text
BAD    Changing a field type in contracts/official_koha_openapi.json so that generation succeeds
GOOD   Adding contracts/checkouts.openapi.json with the renewal operation, copied from the reference
```

**Checked by:** review; `.github/CODEOWNERS` requires the maintainer's review of the official contract

<a id="EX-003"></a>

## EX-003 Never edit generated code by hand; regenerate it

Koha clients are generated by NSwag from the focused contracts, into `Minioasis.Koha/Generated`. That folder belongs to the generator. A hand edit is lost the next time the client is generated, and until then the code no longer matches its contract.

When an approved task changes a focused contract or the generator's configuration:

1. Regenerate only the client for the contract that changed, with the documented command.
2. Inspect the generated diff.
3. Commit the contract, the generator configuration if it changed, and the generated files together.

The generator is pinned as a local .NET tool, so that every machine produces the same code. The exact generation command is written in `docs/running.md` when the first client is generated, and is kept current there.

```text
BAD    Fixing a wrong type directly in Minioasis.Koha/Generated/…
GOOD   Fixing the focused contract (or the generator configuration), then regenerating
```

**Checked by:** review

<a id="EX-004"></a>

## EX-004 Implement authentication once, in the integration project

Authenticating to Koha is a responsibility of `Minioasis.Koha`, shared by every capability that calls Koha. A capability does not obtain, store, or attach a token itself. An adapter asks for the shared, pre-configured Koha client, whose handlers add the token, refresh it, and apply the deadline.

```csharp
// BAD: an adapter that fetches and attaches its own token
var token = await RequestTokenAsync(options.ClientId, options.ClientSecret);
request.Headers.Authorization = new AuthenticationHeaderValue("Bearer", token);

// GOOD: the shared, pre-configured client
var httpClient = httpClientFactory.CreateClient(KohaClientNames.Api);
```

**Checked by:** review

<a id="EX-005"></a>

## EX-005 Use a least-privilege service identity, and keep credentials out of source

Minioasis signs in to Koha as a service account. Give that account only the Koha permissions that approved specs list. A wider permission is a larger loss if the credentials leak.

Credentials are read at run time through ASP.NET configuration, from `MINIOASIS_KOHA_BASE_URL`, `MINIOASIS_KOHA_CLIENT_ID`, and `MINIOASIS_KOHA_CLIENT_SECRET`. The optional `MINIOASIS_KOHA_TIMEOUT_SECONDS` sets the deadline of `EX-011` (spec 001). Real values never enter source control or diagnostic output (`ER-008`).

```jsonc
// BAD: appsettings.json, committed
{ "Koha": { "ClientSecret": "9f2c…" } }
```

```bash
# GOOD: supplied by the environment that runs the application
export MINIOASIS_KOHA_CLIENT_SECRET='…'
```

**Checked by:** review; the maintainer, who creates the Koha service account

<a id="EX-006"></a>

## EX-006 Authenticate to Koha with OAuth 2 client credentials

Minioasis obtains its access token with the OAuth 2 client-credentials grant, through a generated client for Koha's token endpoint. It uses no other grant, no user password, and no static API key. One mechanism means one thing to secure, rotate, and audit.

```csharp
// GOOD: the one token request, made by the shared token provider
var response = await oauthClient.RequestTokenAsync(
    new TokenRequest
    {
        GrantType = "client_credentials",
        ClientId = options.ClientId,
        ClientSecret = options.ClientSecret
    },
    cancellationToken);

// BAD: a second way to sign in, for one feature
request.Headers.Authorization = new AuthenticationHeaderValue("Basic", encodedUserAndPassword);
```

**Checked by:** tests of the token provider, and review

<a id="EX-007"></a>

## EX-007 Use separate HTTP clients for getting a token and for protected calls

The client that requests tokens must not pass through the handler that attaches tokens. If it did, getting a token would itself need a token. Protected API calls use a second client that has the bearer handler.

```csharp
// GOOD: two named clients; only the API client has the bearer handler
services.AddHttpClient(KohaClientNames.OAuth);

services.AddHttpClient(KohaClientNames.Api)
    .AddHttpMessageHandler<KohaDeadlineHandler>()
    .AddHttpMessageHandler<KohaBearerHandler>();

// BAD: the token request sent through the client that carries the bearer handler
var tokenClient = httpClientFactory.CreateClient(KohaClientNames.Api);
```

**Checked by:** tests of the service registration, and review

<a id="EX-008"></a>

## EX-008 Validate every token, cache it until shortly before it expires, and share one refresh

A token response is accepted only if the access token is not blank, its lifetime is positive, and its type is Bearer, compared without regard to case as OAuth 2 requires. Anything else is an authentication failure (`EX-013`), not a token.

A valid token is cached and reused until shortly before it expires, so that Koha is not asked for a token on every request. When several callers need a new token at the same moment, they wait for one refresh and share its result.

```csharp
// BAD: a new token for every call, and no check of what came back
var token = (await oauthClient.RequestTokenAsync(tokenRequest, cancellationToken)).AccessToken;

// GOOD: every caller goes through the provider, which validates, caches, and coordinates refreshes
var token = await tokens.GetAsync(cancellationToken);
```

**Checked by:** tests of the token provider, and review

<a id="EX-009"></a>

## EX-009 After a 401 on a GET, get a new token and retry exactly once

A 401 on a protected GET usually means the cached token was revoked or expired early. Discard the cached token, build the request again, get a new token, and retry once. If the retry also returns 401, return that response: the problem is not the token, and retrying again would loop.

```csharp
// GOOD
var response = await base.SendAsync(request, cancellationToken);
if (response.StatusCode != HttpStatusCode.Unauthorized || request.Method != HttpMethod.Get)
{
    return response;
}

response.Dispose();
tokens.Invalidate();
return await base.SendAsync(CreateRetry(request, await tokens.GetAsync(cancellationToken)), cancellationToken);
```

```csharp
// BAD: retry until it works
while (response.StatusCode == HttpStatusCode.Unauthorized)
```

**Checked by:** tests of the bearer handler, and review

<a id="EX-010"></a>

## EX-010 Never replay a state-changing request automatically, and limit every retry

A request other than GET may already have changed a record in Koha when its response is lost or refused. Sending it again could apply the change twice. So no request other than GET is ever retried automatically, not even after a 401, and every retry that does exist has a fixed limit.

For a workflow that changes state, the approved spec says what happens when Koha fails, times out, or partly succeeds, and whether staff may safely repeat the operation. That design keeps in mind that Koha owns the transaction.

```csharp
// BAD: any failed request is sent again
for (var attempt = 0; attempt < 3; attempt++)
{
    response = await httpClient.SendAsync(Clone(renewalRequest), cancellationToken);
}

// GOOD: only a GET is retried, once (EX-009); a failed write is reported as its spec describes
```

**Checked by:** tests of the bearer handler, the governing spec's "Failure and retry" section, and review

<a id="EX-011"></a>

## EX-011 Put one deadline on all external work

Every interaction with an external system is bounded by one deadline that covers the whole of it: getting a token, sending the request, any retry, and reading the response body. Without it, one slow dependency holds a request, and the staff member waiting for it, indefinitely. When the deadline expires, the result is a dependency failure, not a caller cancellation (`ER-009`).

The deadline is applied in one place, a shared handler on the Koha client (`CD-006`).

```csharp
// BAD: only the wait for response headers is bounded; reading the body can hang for ever
httpClient.Timeout = TimeSpan.FromSeconds(10);
var response = await httpClient.SendAsync(request, HttpCompletionOption.ResponseHeadersRead, cancellationToken);
var body = await response.Content.ReadAsStringAsync(CancellationToken.None);

// GOOD: one linked deadline covers the send and the reading of the body
using var timeout = CancellationTokenSource.CreateLinkedTokenSource(cancellationToken);
timeout.CancelAfter(options.RequestTimeout);
var response = await base.SendAsync(request, timeout.Token);
await response.Content.LoadIntoBufferAsync(timeout.Token);
```

**Checked by:** tests of the deadline handler, and review

<a id="EX-012"></a>

## EX-012 Pass cancellation through every layer

Endpoints, use cases, gateway interfaces, token acquisition, and HTTP operations each accept a `CancellationToken` and pass it on. One layer that drops the token keeps working after the client has gone, and holds a connection to Koha for a result nobody will read.

```csharp
// BAD: the caller's token is dropped
var result = await gateway.RenewLoanAsync(loanId);
var response = await httpClient.SendAsync(request, CancellationToken.None);

// GOOD
var result = await gateway.RenewLoanAsync(loanId, cancellationToken);
var response = await httpClient.SendAsync(request, cancellationToken);
```

**Checked by:** tests that cancel a request, and review

<a id="EX-013"></a>

## EX-013 Report a failure to get a token as an authentication failure

Whatever stops Minioasis from getting a token, the outcome is the same and is reported the same way: a network failure, a timeout, an error status, a response that cannot be read, or a response that fails validation (`EX-008`). Each becomes an authentication failure, which the API answers with a masked 500 (`ER-004`, `ER-006`). The one exception is the caller cancelling, which stays a cancellation (`ER-009`).

```csharp
// BAD: a network error while getting a token escapes as an unhandled exception,
// or is reported as "Koha unavailable" for one cause and "authentication failed" for another

// GOOD: one outcome for every cause
catch (HttpRequestException exception)
{
    logger.LogError("Koha OAuth endpoint could not be reached");
    throw new KohaAuthenticationException("Koha OAuth token acquisition failed.", exception);
}
```

**Checked by:** tests of the token provider, and review
